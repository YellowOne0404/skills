# STM32 CMake 工具链、工程转换与自动调试

脚本都在本 skill 的 `scripts/` 下，只用 Python 标准库。调用时使用脚本的绝对路径。人工安装步骤、下载页和 PATH 对照见 [reference.md](reference.md)。自动化失败时按该文件手工安装，不要另编一套版本号。

三个任务按顺序做，前一步失败就停：

1. 工具链是否齐全（缺了再安装）
2. 工程能否用 CMake + Ninja + `arm-none-eabi-gcc` 编出 `.elf`
3. 识别 ST-Link / J-Link，烧录并做一次 GDB 调试

## 硬性规则

- 已有手写 `CMakeLists.txt`（文件里没有 `Generated by stm32-cmake-devkit`）时，禁止加 `--force`。本仓库这种多产品工程直接编译，不要重写 CMake。
- 根目录有 `product/products.cmake` 和 `hbuild.ps1` / `hbuild.sh` 时，编译入口是 `hbuild`，不要改用 `cmake --preset` 代替。同一构建类型更换产品必须 `--rebuild`。未指定产品序号时先列出序号并询问，不要默认编 1。
- Windows 上 J-Link 只用 SEGGER 软件，不要用 OpenOCD 去驱 J-Link。ST-Link 只用 OpenOCD。
- 同时插着 ST-Link 和 J-Link 时不要猜测，让用户指定 `--probe stlink` 或 `--probe jlink`。
- 芯片型号按这个顺序读取：`--device`、`.embeddedskills/config.json` 的 `jlink.device`、`CMakeLists.txt` 里的 `# STM32_DEVICE:`、唯一的 `.uvprojx` `Device`、唯一的 `.ioc` `Mcu.Name`。同一来源出现多个不同名字就停下来问，不要猜。
- `.bin` 烧录必须带 `--address`。默认只烧 `.elf`。
- ST-Link 只认 PID `3744/3748/374A/374B/3752/374D/374E/374F/3753/3754/3755/3757`。`VID_0483` 的虚拟串口和 DFU 不是探针。同一只复合设备的 `MI_00/01/02` 只算一只。
- 安装会改当前用户的软件和 PATH。用户要求安装环境，或明确要求编译/调试且必需工具缺失时再运行 `install`。先用一句话说明将安装哪些组件。
- 只生成 CubeMX 的 `.ioc`、旁边没有 `Core/` 源码时，不能编译。告知用户先用 CubeMX 生成代码，不要编造 HAL 源文件。

## 1. 检查并安装环境

```bash
python <skill-dir>/scripts/env_setup.py check --json
python <skill-dir>/scripts/env_setup.py install --json
python <skill-dir>/scripts/env_setup.py install --only gcc,cmake,ninja,clangd,openocd --json
python <skill-dir>/scripts/env_setup.py install --with-cubemx --json
```

必需：`arm-none-eabi-gcc`、`arm-none-eabi-gdb`（Linux 上可用 `gdb-multiarch`）、`arm-none-eabi-objcopy`、`arm-none-eabi-size`、`cmake`、`ninja`、`clangd`、`openocd`。

建议：`git`、J-Link（`JLink.exe` / `JLinkExe` 和 GDB Server）。CubeMX、ST-Link 驱动、USB-TTL 驱动不在默认安装里。

Windows 用 winget 安装 GCC / CMake / Ninja / LLVM / Git / J-Link，OpenOCD 优先 `xpm`，否则下载 xPack `0.12.0-7` 到 `%LOCALAPPDATA%/stm32-cmake-devkit/openocd`。Linux 用 `apt` / `dnf` / `pacman`；`sudo -n` 失败时把脚本输出的命令交给用户执行。装完把 bin 目录写入用户 PATH，并在本进程里复检。

退出码：必需工具齐全为 0（J-Link 缺失仍是 0，`status` 为 `partial`）；必需工具缺失为 1。

安装后提醒用户新开终端。随后用这些命令确认，版本号以本机实际输出为准：

```bash
arm-none-eabi-gcc --version
arm-none-eabi-gdb --version
cmake --version
ninja --version
openocd --version
clangd --version
git --version
```

## 2. 转成 CMake 并编译到通过

```bash
python <skill-dir>/scripts/cmake_migrate.py --project <工程根> --json
python <skill-dir>/scripts/cmake_migrate.py --project <工程根> --build --preset Debug --json
python <skill-dir>/scripts/cmake_migrate.py --self-test
```

输入：

- Keil：`*.uvprojx` / `*.uvproj`。读取 Device、Cpu、宏、include、源文件列表。ARMASM 启动文件（含 `AREA`）不会拿去编，改为同树里的 GCC `startup_*.s`。
- CubeMX：`*.ioc` 加上已生成的 `Core/`、`Drivers/`、`Middlewares/`。只收 HAL 非 template 源、对应内核的 GCC FreeRTOS port、`heap_4.c`，以及名字匹配的 GCC 启动文件。

生成物（仅当根目录没有手写 CMake，或该 CMake 带有本 skill 标记时）：

- `cmake/gcc-arm-none-eabi.cmake`：Cortex-M 的 `-mcpu/-mfpu/-mfloat-abi`，`nano.specs`；没有 `syscalls.c` 时再加 `nosys.specs`
- `CMakeLists.txt`、`CMakePresets.json`（Ninja，`Debug` / `Release`，产物在 `build/<preset>/`）
- `CMakeLists.txt` 第一处注释带 `# STM32_DEVICE:`，供烧录脚本识别型号。链接选项用 `SHELL:-T`，map 写到构建目录。
- 缺失时补 `.clangd`、`.vscode/settings.json`、`.vscode/extensions.json`。
- 没有 `.ld` 但 Keil scatter/Cpu 里有地址时，生成 `cmake/generated_flash.ld` 并在结果里警告，要求核对 Flash/RAM。
- F76x/F77x 用 `fpv5-d16`，其余 F7 用 `fpv5-sp-d16`。双核 H745/H747/H755/H757 按 CM7 生成，并在 warnings 里说明 CM4 要单独的启动文件和链接脚本。
- 源码只有 `fputc`、没有 `_write` 或 `__io_putchar` 时给出警告：GCC nano 的 printf 不会从 `fputc` 出去。
- 已有 `.vscode/settings.json` 时不整文件覆盖。只有 `--query-driver` 指向的目录里没有 `arm-none-eabi-gcc` 才改这一项。JSON 解析失败则不动文件并警告。
- 生成工程时，若 `.embeddedskills/config.json` 里还没有 `jlink.device`，补上转换得到的型号，不覆盖已有型号。

`status=already-cmake` 表示没有改构建文件。多产品工程若要编译，让用户给出序号后执行：

```powershell
.\hbuild.ps1 <id> Debug -b
```

```bash
./hbuild.sh <id> Debug -b
```

单产品生成工程：

```bash
cmake --preset Debug
cmake --build --preset Debug
```

编译失败时先看 JSON 里的 `errors`。只修本次转换引入的问题（漏掉的 include、选错的启动文件、缺链接脚本、重复的 port）。不要为了消警告去改业务源码。修完重新 `--build`。成功标准是退出码 0，且 `build/<preset>/firmware.elf` 或目标 `.elf` 存在。

`--build` 在多产品仓库上如果没有 `--product-id` 会直接失败，避免悄悄编成产品 1。

## 3. 识别探针、烧录、调试

```bash
python <skill-dir>/scripts/probe_debug.py detect --project <工程根> --json
python <skill-dir>/scripts/probe_debug.py flash --project <工程根> --elf build/Debug/firmware.elf --json
python <skill-dir>/scripts/probe_debug.py flash --project <工程根> --elf build/Debug/firmware.bin --address 0x08000000 --verify-boot --json
python <skill-dir>/scripts/probe_debug.py debug --project <工程根> --elf build/Debug/firmware.elf --json
python <skill-dir>/scripts/probe_debug.py diagnose --project <工程根> --json
python <skill-dir>/scripts/probe_debug.py size-report --project <工程根> --elf build/Debug/firmware.elf --json
python <skill-dir>/scripts/probe_debug.py log --project <工程根> --json
python <skill-dir>/scripts/probe_debug.py gen-launch --project <工程根> --elf build/Debug/firmware.elf --json
python <skill-dir>/scripts/probe_debug.py --self-test
```

识别规则：当前 USB 设备里 ST-Link 的 VID/PID（见硬性规则）视为 ST-Link，`VID_1366` 视为 J-Link。两者都在时退出并要求 `--probe` 或环境变量 `FLASH_PROBE`。只写了 `--probe` 时不要求这只探针此刻一定被枚举到，但烧录失败要原样返回探针输出。

- ST-Link：`openocd -f interface/stlink.cfg -f target/<family>.cfg -c "program <elf> verify reset exit"`。`.bin` 时改为 `program <file> <address> verify reset exit`。
- J-Link：命令文件第一行 `log <临时日志>`，然后 `h` / `loadfile` 或 `loadbin <文件> <地址>` / `r` / `g` / `qc`，`-if SWD -speed 4000 -autoconnect 1 -NoGui 1`。管道里的标准输出不可靠，以日志文件为准；日志可能是 UTF-16。成功必须同时满足退出码 0、日志里有 `O.K.` 或 `Flash download`，且没有 `cannot connect` / `failed to` / `no device found`。
- `debug`：拉起 OpenOCD（GDB 3333）或 `JLinkGDBServerCL`（GDB 2331），再用 GDB 执行 `break main`、`continue`、`bt`、`info locals`。30 秒内没有停在 `main` 就结束进程并返回已有输出。
- `diagnose`：不复位。OpenOCD 加 `reset_config none`，J-Link GDB Server 加 `-noreset`。GDB 只做 `monitor halt`、`info registers`、`bt`，并读 `CFSR/HFSR/MMFAR/BFAR`（`0xE000ED28/2C/34/38`）。不要 `continue`。ELF 可以没有。成功看寄存器或 CFSR，不要求停在 `main`。
- `size-report`：`arm-none-eabi-size -A` 和 `nm -S --size-sort`。唯一的 `*FLASH*.ld` 用来把段按 `MEMORY` 归区。多个链接脚本时不猜，只列符号。
- `log` 和 `flash --verify-boot`：烧录成功后再抓约 3 秒。优先同目录的 `JLinkRTTLogger`，否则用 `.embeddedskills/config.json` 的 `serial.port` / `baudrate`。日志为空时 `status=partial`，烧录本身仍然算成功。
- `gen-launch`：没有 `.vscode/launch.json` 时写入 J-Link 与 ST-Link 的 Launch（复位停到 `main`）和 Attach（不写 `runToEntryPoint`）。工程里只有一个 SVD，或文件名包含芯片型号时，写入 `svdFile`。已有 `launch.json` 则写到 `.vscode/launch.stm32-cmake.json`。

烧录成功的标志：OpenOCD 输出 `Verified OK` 或 `Verify OK`，或 J-Link 日志里有 `O.K.` / `Flash download`。把探针类型、文件路径和这句结果告诉用户。死机时用 `diagnose` 的 CFSR 位（`IACCVIOL`、`PRECISERR`、`UNDEFINSTR`、`UNALIGNED`、`DIVBYZERO` 等）说明原因，不要只说退出码。

## 输出约定

脚本默认给人读的文本。Agent 调用时加 `--json`。字段为 `status`（`ok` / `partial` / `error`）、`action`、`summary`、`details`，可能带 `next_actions`。不要把 JSON 再包一层解释；用 `summary` 和失败时的 `errors` 向用户复述。
